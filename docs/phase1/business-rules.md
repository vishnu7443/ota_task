# Business Rules Catalogue

**Rule Classification Tags (Required Quality Standard):**
- `[OFFICIAL]` — Explicitly mandated or stated in `Problem Statement - Winter Internship Application - 2026.docx`.
- `[ASSUMPTION]` — Reasonable business/accounting rule chosen where the official document left flexibility or ambiguity (Section 10 invites documented assumptions).
- `[ENGINEERING]` — Technical correctness / integrity invariant derived from Section 7.

---

## 1. Order Status Transitions (`BR-ORD`)

| ID | Rule | Tag | Rationale & Enforcement |
| --- | --- | --- | --- |
| **BR-ORD-01** | **Allowed Order States:** `DRAFT` -> `SUBMITTED` -> (`CORRECTION_REQUESTED` <-> `SUBMITTED`) -> `APPROVED` -> `INVOICED` -> `DISPATCHED`; terminal cancellation states: `REJECTED` (pre-approval), `CANCELLED` (pre-invoice or via Credit Note post-invoice). | `[OFFICIAL]` + `[ASSUMPTION]` | Section 4.1 explicitly mentions `submitted, approved, invoiced, dispatched`; Section 4.2 mentions `approve or reject`; User prompt explicitly specifies `requests correction` (`CORRECTION_REQUESTED`). |
| **BR-ORD-02** | **Salesman Edit Lock:** Once an order enters `APPROVED`, `INVOICED`, `DISPATCHED`, or `REJECTED`, the Salesman cannot modify or delete it. Only `DRAFT` or `CORRECTION_REQUESTED` orders are editable by the owning Salesman. | `[ASSUMPTION]` | Prevents mid-billing price/quantity tampering after factory verification. |
| **BR-ORD-03** | **Idempotent Order Submission:** Every mobile order submission must carry a client-generated `client_order_id` (`UUID`). Re-submitting the same `client_order_id` due to weak network must return the existing order without creating a duplicate. | `[ENGINEERING]` | Addresses weak mobile network (`Section 3`) and duplicate submission edge case (`EC-02`). |
| **BR-ORD-04** | **Approval Prerequisite:** Order must have at least one line item (`qty > 0`), valid active customer with State defined, and non-negative prices before transition to `APPROVED`. | `[OFFICIAL]` | Place of supply (Customer State) is mandatory to compute CGST/SGST vs IGST later. |
| **BR-ORD-05** | **Pre-Invoice Edit Audit:** Factory Admin may edit order quantities or unit prices while `SUBMITTED` or `CORRECTION_REQUESTED` (or `APPROVED` prior to `INVOICED`), provided a reason is entered and old/new values are written to the Audit Log. | `[OFFICIAL]` + `[ASSUMPTION]` | Section 4.2 allows Admin to edit quantities or prices; Section 7 requires audit traceability. |

## 2. Stock Availability, Reservations & Insufficient Stock (`BR-STK` / `BR-AVL`)

| ID | Rule | Tag | Rationale & Enforcement |
| --- | --- | --- | --- |
| **BR-AVL-01** | **Two-Metric Availability Check:** System tracks `On-Hand Stock` (sum of `StockLedger`) and `Reserved Stock` (sum of undispached qty across `APPROVED` + `INVOICED` orders). `Available Stock = On-Hand - Reserved`. | `[ASSUMPTION]` | Resolves race condition between Approval (`BR-ORD`) and Dispatch (`BR-DSP`) so two salesmen/admins cannot oversell the same 88 packets simultaneously (`EC-03`). |
| **BR-AVL-02** | **Non-Blocking Mobile Capture, Blocking Approval:** Salesman *can* submit an order even when `Ordered Qty > Available Stock` (e.g., Distributor B ordering `120` when `88` are available). However, Admin **cannot** blindly approve/dispatch beyond `Available Stock` without resolving the shortage. | `[OFFICIAL]` + `[ASSUMPTION]` | Benchmark Step 6 explicitly expects Salesman B to place the 120-packet order and Admin/system to flag `"Shortage of 32 packets"`. |
| **BR-AVL-03** | **Insufficient Stock Handling Options:** When `Ordered Qty > Available Stock`, system flags exact `Shortage Qty = Ordered - Available` and restricts Admin to: (a) **Hold / Await Production** (order remains unapproved/pending until production output covers it), (b) **Edit Qty to Available** (`<= 88` with customer agreement & audit note), (c) **Partial Approval/Dispatch** (if Should/Optional split fulfillment is enabled), or (d) **Reject Order**. | `[OFFICIAL]` + `[ASSUMPTION]` | Section 4.2 states *"Before approval, the system shows whether finished-goods stock covers the order... Partial dispatch and returns are optional."* Negative finished-goods stock is strictly forbidden (`BR-STK-02`). |

## 3. Invoice Numbering, GST & Tax Calculation (`BR-TAX` / `BR-INV`)

| ID | Rule | Tag | Rationale & Enforcement |
| --- | --- | --- | --- |
| **BR-INV-01** | **Financial Year Sequential Numbering:** Posted GST tax invoices use a strict, gap-free, FY-partitioned sequence (Indian FY = April 1 to March 31), e.g., `INV/2026-27/0001`. Draft/rejected orders do **not** consume invoice numbers. Credit notes carry an independent FY sequence (`CN/2026-27/0001`). | `[OFFICIAL]` + `[ASSUMPTION]` | Section 4.2 mandates *"invoice numbering by financial year"*; sequential gap-free posting is an Indian GST statutory compliance expectation. |
| **BR-INV-02** | **1-to-1 Order-to-Invoice (Baseline):** In baseline flow, approving an order generates one `POSTED` GST invoice covering the approved order lines (or separate explicit "Raise Invoice" action immediately after Approval). | `[OFFICIAL]` | Matches Section 5 Step 5 ("approves it, raises the GST invoice"). |
| **BR-TAX-01** | **CGST/SGST vs IGST by Place of Supply:** Compare Factory State (`Tamil Nadu`, code `33`) against Customer's Place-of-Supply State (`State Code`):<br>- **Same State (`Customer State == Factory State`):** Intra-state supply -> `CGST = tax_rate / 2` and `SGST = tax_rate / 2` (e.g., `2.5% + 2.5%` for `5%` GST).<br>- **Different State (`Customer State != Factory State`):** Inter-state supply -> `IGST = tax_rate` (e.g., `5.0%` for Karnataka). | `[OFFICIAL]` | Section 4.2 & Section 5 Checks (`Retailer A TN -> CGST + SGST`; `Distributor B KA -> IGST`). |
| **BR-TAX-02** | **Taxable Value & Tax Base:** Line `Taxable Value = qty × unit_price_before_tax - line_discount` (discount = 0 in baseline). `Tax Amount` is calculated on `Taxable Value` per HSN/tax-rate bucket. | `[OFFICIAL]` | Benchmark selling price `₹50/packet before tax`, `150 × 50 = ₹7,500`, `2.5% = ₹187.50`. |
| **BR-TAX-03** | **Deterministic Integer-Paisa Money & Rounding:** All currency amounts are stored as integer **paise** (`1 INR = 100 paise`, `BIGINT`) or exact `Decimal` rounded to 2 decimal places using `ROUND_HALF_UP`. Intermediate tax calculations compute `(taxable_paise * rate_bps) / 10000` (where `2.5% = 250 bps`, `5% = 500 bps`) with `ROUND_HALF_UP` per invoice line/tax head so `CGST == SGST` always holds identically on intra-state invoices. | `[OFFICIAL]` + `[ENGINEERING]` | Section 7 strictly prohibits floating-point arithmetic (`float`) for money. |
| **BR-INV-03** | **Mandatory GST Invoice Fields:** Seller Legal Name, Address, GSTIN, State & Code; Invoice Number & Date; Buyer Name, Address, State & Code (Place of Supply), Buyer GSTIN (if registered); Line items with HSN code, Qty, Unit, Rate, Taxable Value; Tax breakdown (`CGST % & ₹`, `SGST % & ₹`, or `IGST % & ₹`); Grand Total (digits + words). | `[OFFICIAL]` | Section 4.2 explicitly specifies GSTIN, HSN code, taxable value, CGST/SGST or IGST, FY invoice number, and PDF export. |

## 4. Dispatch, Returns & Cancellations (`BR-DSP` / `BR-RET`)

| ID | Rule | Tag | Rationale & Enforcement |
| --- | --- | --- | --- |
| **BR-DSP-01** | **Dispatch Triggers Finished-Goods Stock Deduction:** Recording Dispatch creates an immutable `DISPATCH_OUT` entry in the Stock Ledger reducing `Finished Goods` by dispatched packet quantity and releasing the corresponding `Reserved Stock`. Invoice generation alone does **not** deduct physical stock. | `[OFFICIAL]` | Section 2 diagram & Section 4.2 explicitly state *"Dispatch reduces finished-goods stock"*. |
| **BR-DSP-02** | **No Double Carton Deduction on Dispatch:** Packaging cartons (`1 carton = 20 packets`) are consumed and deducted from packaging stock during **Production Run packing** (Section 5 Step 3). Dispatching finished packets deducts **only** Finished Goods SKU stock (`packets`), unless separate outer transit re-packing is explicitly modelled later. | `[ASSUMPTION]` | Prevents double-counting the 9 cartons already consumed in Step 3 (`30 - 9 = 21` cartons). |
| **BR-DSP-03** | **Partial Dispatch (Optional / Should-Have Mode):** If enabled, total dispatched qty across dispatch notes for an invoice cannot exceed invoiced qty (`sum(dispatched) <= invoiced`), and each dispatch note posts its own `DISPATCH_OUT` ledger line. Order status displays `PARTIALLY_DISPATCHED` until `100%` dispatched. | `[OFFICIAL]` + `[ASSUMPTION]` | Section 4.2 lists partial dispatch as optional; rules safeguard against over-dispatching. |
| **BR-RET-01** | **Posted Invoice Cancellation via Credit Note Only:** A `POSTED` invoice **cannot** be deleted or edited directly. Cancelling (full or partial return) requires issuing a **Credit Note (`CN`)** referencing the original `INV`.<br>- If **not yet dispatched**: Credit Note reverses Customer AR & GST outward tax liability and releases the order's `Reserved Stock`.<br>- If **already dispatched**: Credit Note reverses AR & GST liability, and a linked **Sales Return** step either restores sellable goods to Finished Goods (`CREDIT_RETURN_IN`) OR logs damaged/expired returns to a `SCRAP / QUARANTINE` ledger without polluting sellable stock! | `[OFFICIAL]` + `[ASSUMPTION]` | Section 7 explicitly mandates *"posted invoices are cancelled with a credit note, not deleted."* Food returns may be expired/damaged, hence sellable vs scrap distinction is vital. |

## 5. Payments, Allocation & Customer Outstanding (`BR-PAY`)

| ID | Rule | Tag | Rationale & Enforcement |
| --- | --- | --- | --- |
| **BR-PAY-01** | **Invoice-Targeted Payment Allocation:** When Factory Admin records a customer payment, it is validated (`amount > 0`) and explicitly allocated against one or more open `POSTED` invoices (default: selected invoice in UI, e.g. `₹4,000` against Retailer A's `₹7,875` invoice). | `[OFFICIAL]` | Matches Section 4.2 (*"Payments received are recorded against invoices"*) and Step 7. |
| **BR-PAY-02** | **Outstanding Balance Invariant:**<br>- `Invoice Outstanding = Invoice Grand Total - Sum(Allocated Payments) - Sum(Linked Credit Notes)`<br>- `Customer Outstanding = Sum(Open Invoice Outstandings) - Unallocated Customer Advance Credits`<br>Invoice payment status auto-updates: `UNPAID` (`paid == 0`), `PARTIALLY_PAID` (`0 < paid < total`), `PAID` (`paid == total`). | `[OFFICIAL]` + `[ASSUMPTION]` | Matches Retailer A Check: `₹7,875 - ₹4,000 = ₹3,875`. |
| **BR-PAY-03** | **Overpayment & Duplicate Guard:** System rejects payment allocation exceeding an invoice's remaining balance unless the excess is explicitly recorded as an `UNALLOCATED_ADVANCE`. Submitting identical `(customer, amount, date, reference_no)` or duplicate `idempotency_key` triggers a duplicate warning/block (`EC-09`). | `[ASSUMPTION]` | Prevents accidental double-entry of payments from bank statements or double-clicks. |
| **BR-PAY-04** | **Receivables Ageing Buckets:** Open invoice balances are bucketed by age in days `(Report As-Of Date - Invoice Date)` (or vs Due Date if credit terms are configured): `0–30 days`, `31–60 days`, `61–90 days`, `> 90 days`. | `[ASSUMPTION]` | Fulfils Section 4.6 *"outstanding (receivables) by customer with ageing"*. |

## 6. BOM, Unit Conversions, Production & Variances (`BR-PRD` / `BR-UOM` / `BR-VAR`)

| ID | Rule | Tag | Rationale & Enforcement |
| --- | --- | --- | --- |
| **BR-UOM-01** | **Exact Unit Dimension Families & Conversions:** Every item belongs to one primary measurement dimension:<br>- **Mass (Base = `gram`, g):** `1 kg = 1,000 g` (stored with exact decimal `1.2 kg = 1200 g`)<br>- **Volume (Base = `millilitre`, ml):** `1 L = 1,000 ml` (`10.5 L = 10,500 ml`)<br>- **Count (Base = `piece` / `packet`):** `1 piece = 1 unit`<br>Cross-dimension conversions (e.g., `kg` to `L`) are **rejected** unless an explicit item-specific density/conversion exists. Product-level pack conversions link count to weight/cartons (e.g., `1 packet Murukku 200 g = 200 g net`; `1 carton = 20 packets`). | `[OFFICIAL]` + `[ENGINEERING]` | Section 4.3 requires exact conversions across `kg, g, litres, pieces, packets, cartons` without rounding drift. |
| **BR-PRD-01** | **BOM Scaling Rule:** Each BOM defines inputs per **1 standard batch** (`expected_yield_packets`, e.g., `200`). For a run of `batch_multiplier = B` (`B = 1.0` in benchmark):<br>- `Planned Raw Qty = BOM Qty per batch × B`<br>- `Expected Output Packets = expected_yield_packets × B`. | `[OFFICIAL]` | Supports half batches (`0.5`), standard (`1.0`), or multi-batch runs (`2.0`) directly. |
| **BR-PRD-02** | **Automatic Dual Stock Update:** Completing a production run atomically deducts all issued raw materials and packaging (`PROD_ISSUE_OUT` / `PACKAGING_DAMAGE_OUT`) and adds `actual_good_packets` to Finished Goods (`PROD_OUTPUT_IN`) in the Stock Ledger. Negative raw/packaging stock is blocked before posting. | `[OFFICIAL]` | Section 4.3 & Section 5 Checks (`120 kg`, `19.5 L`, `306 pouches`, `238 pkts`). |
| **BR-PRD-03** | **Damaged Packaging Rule:** Packaging consumed during a run separates into `good_units_used` (e.g., `188 pouches`, `9 cartons`) and `damaged_or_wasted_units` (e.g., `6 pouches`). Both reduce packaging inventory (`188 + 6 = 194` pouches deducted; `500 - 194 = 306`). | `[OFFICIAL]` | Explicitly tested in Benchmark Step 3 (`Pouches closing balance: 306 = 188 used + 6 damaged`). |
| **BR-VAR-01** | **Raw Material Consumption Variance:**<br>`Consumption Variance % = ((Actual Issued - Planned Batch Qty) / Planned Batch Qty) × 100`<br>Positive `%` = excess consumption (loss/over-issue); Negative `%` = under-consumption.<br>Example: Oil `((10.5 - 10.0) / 10.0) × 100 = +5.0%`. | `[OFFICIAL]` | Matches Section 5 Check (`Oil consumption variance: +5%, flagged`). |
| **BR-VAR-02** | **Yield Variance:**<br>`Yield Variance % = ((Actual Good Output - Expected Batch Output) / Expected Batch Output) × 100`<br>Negative `%` = lower yield than recipe target.<br>Example: Packets `((188 - 200) / 200) × 100 = -6.0%`. | `[OFFICIAL]` | Matches Section 5 Check (`Yield variance: 188 vs 200 expected, -6%, flagged`). |
| **BR-VAR-03** | **Packaging Consumption Variance Rule (Explicit Assumption):** Compare actual total packaging consumed (`good + damaged`) against **output-scaled standard** (`1 pouch per good packet` -> `194 vs 188 = +6 pouches = +3.19%` wastage!) AND display batch BOM planned qty (`200`) for side-by-side clarity. (For cartons, compare `9` used vs `floor(188/20) = 9` expected whole cartons = `0` variance, while noting `8` loose packets and `10` batch BOM cartons — see `AMB-03`). | `[ASSUMPTION]` | Comparing `194` vs `200` would falsely show `-3%` favorable usage despite 6 wasted pouches; comparing against output-scaled requirement (`188`) exposes the true `+3.19%` packaging wastage! |
| **BR-VAR-04** | **Tolerance Flagging Threshold:** Configurable system tolerance `default = 3.0%` (from Section 4.3 example). Any material consumption variance or yield variance with `abs(variance_pct) > 3.0%` automatically generates a **Variance Alert** on the Production Run and Owner Dashboard. (`>` vs `>=` boundary explicitly documented as strictly greater than `3.0%`, or `>= 3.0%` if strict — both `+5%` and `-6%` trigger under either!). | `[OFFICIAL]` + `[ASSUMPTION]` | Section 4.3 states `"(for example 3%)"`; Section 5 flags `+5%` and `-6%`. |

## 7. Stock Ledger, Valuation, Costing & Audit Trail (`BR-LED` / `BR-CST` / `BR-AUD`)

| ID | Rule | Tag | Rationale & Enforcement |
| --- | --- | --- | --- |
| **BR-LED-01** | **Ledger-Derived Stock Integrity:** Stock balances for Raw Materials, Packaging Materials, and Finished Goods must **never** be manually overwritten. Current balance is always equal to `Opening Balance + Sum(Receipts) - Sum(Issues/Sales) ± Sum(Logged Adjustments)`. Materialized balance caches (if used for speed) must strictly reconcile 100% with the `StockLedger`. | `[OFFICIAL]` + `[ENGINEERING]` | Section 4.4 & Section 7 explicitly forbid overwriting stock numbers without ledger movements. |
| **BR-LED-02** | **Mandatory Source Document Link:** Every row in `StockLedger` must carry a non-null `(source_type, source_id)` linking to `OPENING_SEED`, `PURCHASE`, `PRODUCTION_RUN`, `DISPATCH`, `CREDIT_NOTE_RETURN`, or `STOCK_ADJUSTMENT` (which requires reason + approver). | `[OFFICIAL]` | Section 7 Traceability rule. |
| **BR-LED-03** | **No Silent Negative Stock:** Standard operational transactions (production issues, packaging consumption, dispatches) must reject any movement that would drive an item's ledger balance below `0`. | `[ASSUMPTION]` + `[ENGINEERING]` | Prevents phantom inventory and forces purchases/production receipts or explicit physical count adjustments before dispatch. |
| **BR-CST-01** | **Raw & Packaging Valuation Method (Choice Needed — FIFO Recommended):**<br>- **Recommended (`FIFO`):** Each receipt creates a cost lot (`qty_remaining, unit_cost_paise`); issues consume oldest lots first (`40 kg flour` consumes from `100 kg @ ₹42` opening lot -> `₹1,680.00`).<br>- **Alternative (`Moving Weighted Average`):** Each receipt recalculates running average unit cost (`(100×42 + 60×45)/160 = ₹43.125/kg` -> `40 × 43.125 = ₹1,725.00`).<br>Selected method applies consistently across all material issues and Stock Valuation reports. | `[OFFICIAL]` + `[ASSUMPTION]` | Section 4.5 asks us to pick and justify one of last price, weighted average, or FIFO. See `benchmark-analysis.md` for full comparison (`DEC-01`). |
| **BR-CST-02** | **Damaged Packaging in Run Cost:** Cost of all pouches (`188 good + 6 damaged = 194 × ₹2.50 = ₹485.00`) and cartons (`9 × ₹15 = ₹135.00`) consumed in the production run is absorbed into that run's total cost (`₹620.00`), so cost per good packet reflects actual wastage. | `[ASSUMPTION]` | Prevents packaging wastage from disappearing from unit economics (`AMB-04`). |
| **BR-CST-03** | **Overhead Allocation Rule:**<br>- **Tier 1 (Direct Run Overheads):** Labour (`₹1,200`) and gas/power (`₹600`) logged directly against a run are absorbed 100% by that run (`₹1,800`).<br>- **Tier 2 (Monthly Shared Overheads — Optional Pool):** Monthly factory overheads (rent, supervisor salary) entered without a run ID are allocated across completed runs in that month proportional to **good packets produced** (or **standard batch count**). | `[OFFICIAL]` + `[ASSUMPTION]` | Satisfies Section 4.5 (`per run or per month, allocated by a rule you choose and explain`) and handles Benchmark Step 8 cleanly. |
| **BR-CST-04** | **Cost per Packet & Gross Margin:**<br>`Cost per Good Packet = Total Run Cost (Materials + Packaging + Overheads) / Actual Good Packets` (rounded to nearest paisa via `ROUND_HALF_UP`).<br>`Gross Margin per Packet = Selling Price Before Tax - Cost per Good Packet` (`₹50.00 - Cost`). | `[OFFICIAL]` | Satisfies Section 4.5 & Benchmark Check. |
| **BR-AUD-01** | **Immutable Audit Trail on Edits & Sensitive Actions:** Any edit to an order (qty/price), invoice, credit note, production run, BOM, price list, or stock adjustment writes an immutable `AuditLog` record containing: `actor_user_id`, `actor_role`, `timestamp_ist`, `action`, `entity_type`, `entity_id`, `before_snapshot`, `after_snapshot`, and `reason`. | `[OFFICIAL]` + `[ENGINEERING]` | Section 7 explicitly mandates audit trail on edits to invoices and production runs with user and time. |
