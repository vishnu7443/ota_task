# End-to-End Operational Workflows

**Source Basis:** Official Problem Statement Sections 2, 4, 5, 7  
**Traceability Rule:** Every step traces `Initiating Action -> Validation & Decision -> State Transition -> Ledger / Financial Impact -> Final Outcome`.

---

## 1. Workflow A: Sales Loop (Field Order to Collection)

### End-to-End Traceability Matrix

| Step | Actor & Channel | Initiating Action | System Validation & Decision Logic | State Transition | Database / Ledger / Accounting Outcome |
| --- | --- | --- | --- | --- | --- |
| **A1** | Salesman (Mobile) | Logs in with credentials | Authenticate user; verify role = `SALESMAN` and active flag; issue scoped session token. | Session Active | Audit/access event logged; UI restricted to salesman's routes/customers & own orders. |
| **A2** | Salesman (Mobile) | Selects existing customer (Retailer/Distributor) | Verify customer is `ACTIVE` (and within salesman visibility scope if territory-filtered). Retrieve customer state & customer-specific price overrides (if any). | Order Draft Initialized | Customer context + state (`Tamil Nadu` vs `Karnataka`) bound to draft for downstream GST preview. |
| **A3** | Salesman (Mobile) | Adds products (SKUs) & quantities | Validate `qty > 0` integer packets (or cartons converted to packets). Fetch active unit selling price from Price List (`₹50.00/pkt` for Murukku 200 g). Calculate line subtotal using integer paise. | Draft Lines Populated | Optional read-only advisory badge shows whether current factory stock covers qty (non-blocking at order entry — see `AMB-02`). |
| **A4** | Salesman (Mobile) | Reviews summary & taps **Submit Order** | Generate/attach client-side `idempotency_key` (`UUID`). Validate non-empty lines, positive qtys, valid customer. If network drops before response, hold payload in local storage and retry with same `idempotency_key`. | `DRAFT` -> `SUBMITTED` | Central backend persists `SalesOrder` (`SUBMITTED`) + `SalesOrderLines` atomically; duplicate retry returns existing order without creating a second order. **No stock deducted yet.** |
| **A5** | Factory Admin (Desktop) | Opens **Incoming Orders Queue** | Filter `SUBMITTED` / `CORRECTION_REQUESTED` orders. For each line, compute `On-Hand FG Stock` and `Reserved FG Stock` (`Available = On-Hand - Reserved`). Compare `Ordered Qty` vs `Available Qty`. | Viewed by Admin | Displays stock status badge: `IN STOCK (238 avail vs 150 req)` or `SHORTAGE (88 avail vs 120 req -> Short by 32)`. |
| **A6** | Factory Admin (Desktop) | Verifies price, qty, customer & chooses action | **Branch 1 — Request Correction:** Enter note -> order returns to `CORRECTION_REQUESTED`.<br>**Branch 2 — Reject:** Enter mandatory rejection reason -> order closes as `REJECTED`.<br>**Branch 3 — Edit & Approve:** Admin may edit qty/price (logged in Audit Log with before/after). Verify `Available Stock >= Approved Qty`. If short, block approval (see `EC-04`). | `SUBMITTED` -> `APPROVED` (or `REJECTED` / `CORRECTION_REQUESTED`) | On `APPROVED`: `SalesOrder` locked for salesman edits; **soft stock reservation** increases `Reserved Qty` by approved qty (`150` pkts); Audit Log records approval user & timestamp. |
| **A7** | Factory Admin (Desktop) | Clicks **Generate GST Invoice** on approved order | Verify order is `APPROVED` and not yet invoiced. Compare Seller State (`Tamil Nadu`, `33`) vs Customer State (`Tamil Nadu` = Intra-state -> `CGST 2.5% + SGST 2.5%`; `Karnataka` = Inter-state -> `IGST 5%`). Assign next gap-free FY sequence number (`INV/2026-27/0001`). Compute exact integer-paisa line & tax totals. | Order `APPROVED` -> `INVOICED`; Invoice `POSTED` (`UNPAID`) | `TaxInvoice` + `TaxInvoiceLines` saved immutably; **Customer Receivable (`AR`)** increases by Grand Total (`₹7,875.00`); GSTR outward supply record becomes queryable; **PDF Invoice** generated and shareable link prepared. |
| **A8** | Factory Admin (Desktop) | Records **Dispatch** against invoiced (or approved) order | Verify Invoice is `POSTED` and dispatch qty `<=` remaining undispached qty and `<= On-Hand FG Stock`. Capture dispatch date & transport/challan reference. | Order `INVOICED` -> `DISPATCHED`; Dispatch `COMPLETED` | **Atomic transaction:**<br>1. `DispatchNote` created.<br>2. **Stock Ledger (`DISPATCH_OUT`)** written for `-150 packets` linked to `DSP`/`INV`, reducing Finished Goods On-Hand (`238 -> 88`).<br>3. Soft reservation (`150`) released.<br>(Note: Cartons were already deducted at production packing; not deducted again.) |
| **A9** | Factory Admin (Desktop) | Records **Payment Received** from customer | Validate `payment_amount > 0` and `<= customer/invoice open balance` (or allocate excess to advance credit if permitted). Verify payment reference isn't an accidental duplicate submission. | Invoice `UNPAID` -> `PARTIALLY_PAID` (or `PAID`) | `PaymentReceipt` saved (`₹4,000.00`); allocation links payment to `INV/2026-27/0001`; Invoice paid total = `₹4,000.00`, outstanding = `₹3,875.00`; Customer AR ledger balance drops from `₹7,875.00` to `₹3,875.00`. |
| **A10** | Salesman (Mobile) & Auditor (Desktop) | Views tracking & receivables | Query order status and invoice payment balance. | Read-only Query | Salesman sees order transitioned to `DISPATCHED` and Retailer A sales total; Accountant sees transaction in Sales Register, GST Summary, Stock Ledger, and AR Ageing. |

> **Important Note on Invoice Cancellation (Audit Rule, Section 7):** Once `TaxInvoice` is `POSTED`, it **cannot be deleted or silently edited**. If cancelled, Admin creates a **Credit Note (`CN/2026-27/0001`)** referencing the invoice, reversing Customer AR and GST liability (and creating a `CREDIT_RETURN_IN` stock ledger movement only if dispatched goods are physically returned in sellable condition).

## 2. Workflow B: Production Loop (Purchase to Cost per Packet)

### End-to-End Traceability Matrix

| Step | Actor & Channel | Initiating Action | System Validation & Decision Logic | State Transition | Database / Ledger / Accounting Outcome |
| --- | --- | --- | --- | --- | --- |
| **B1** | Production Supervisor / Admin (Desktop/Tablet) | Records **Raw/Packaging Material Purchase** | Select supplier, item (`Flour`), quantity (`60`), unit (`kg`), rate (`₹45.00/kg`), date, supplier bill ref. Validate `qty > 0`, `rate >= 0`. Convert unit to item's canonical base unit (`60 kg -> 60,000 g`). | Purchase `POSTED` | 1. `PurchaseReceipt` saved (`₹2,700.00`).<br>2. **Stock Ledger (`PURCHASE_IN`)** written (`+60 kg` Flour, `100 -> 160 kg`), linked to `PUR` ID.<br>3. Cost layer (`FIFO`: `60 kg @ ₹45`) or Moving Average (`₹43.125/kg`) updated.<br>4. Appears in Purchase Register. |
| **B2** | Production Supervisor / Admin (Desktop) | Maintains **Product BOM** | Define finished SKU (`Murukku 200 g`), expected batch yield (`200 packets`), and input lines (`40 kg` flour, `10 L` oil, `1.2 kg` spice mix, `200` pouches, `10` cartons). Validate compatible unit dimensions (mass/volume/count) and positive quantities. | BOM `ACTIVE` (Versioned) | BOM saved as version `v1`. Editing an active BOM creates a new version (`v2`) so past production runs retain historical BOM traceability. |
| **B3** | Production Supervisor (Tablet/Desktop) | **Starts Production Run** & **Issues Raw Materials** | Select SKU (`Murukku 200 g`), active BOM, batch multiplier (`1.0` -> expected `200 packets`). Enter actual raw materials issued (`40 kg` flour, `10.5 L` oil, `1.2 kg` spice mix). Validate each item's `On-Hand Stock >= Actual Issued Qty` (block negative RM stock). | Run `IN_PROGRESS` | **Atomic transaction:**<br>1. `ProductionRun` created with planned raw qty snapshot from BOM.<br>2. **Stock Ledger (`PROD_ISSUE_OUT`)** entries written immediately for `-40 kg` flour (`160 -> 120 kg`), `-10.5 L` oil (`30 -> 19.5 L`), `-1.2 kg` spice (`5 -> 3.8 kg`).<br>3. Material consumption cost computed using active valuation method (FIFO/WAvg) and locked on the issue lines. |
| **B4** | Production Supervisor (Tablet/Desktop) | Records **Actual Output, Wastage & Packaging Used** -> **Completes Run** | Enter `actual_good_packets` (`188`), `damaged_pouches` (`6`), `cartons_used` (`9`), optional scrap/wastage weight or remarks. Validate `pouches_used (188 + 6 = 194) <= On-Hand pouches (500)` and `cartons_used (9) <= On-Hand cartons (30)`. | Run `IN_PROGRESS` -> `COMPLETED` | **Atomic transaction:**<br>1. **Stock Ledger (`PROD_OUTPUT_IN`)** written for `+188 packets` Murukku 200 g (`50 -> 238 pkts`), linked to `PRD` ID.<br>2. **Stock Ledger (`PROD_ISSUE_OUT` / `PACKAGING_DAMAGE_OUT`)** written for `-188` good pouches & `-6` damaged pouches (`500 -> 306`), and `-9` cartons (`30 -> 21`).<br>3. Run locked against silent edits (subsequent corrections require logged adjustment/audit trail). |
| **B5** | System (Automated upon B3/B4) | Calculates **Consumption & Yield Variances** | Compare:<br>- **Raw Consumption Variance:** `(Actual - Planned) / Planned × 100%` (Oil: `(10.5 - 10)/10 = +5.0%`).<br>- **Yield Variance:** `(Actual Good - Expected Yield) / Expected Yield × 100%` (`(188 - 200)/200 = -6.0%`).<br>- **Packaging Variance:** Compare `194` pouches vs standard (see `AMB-03` for batch-200 vs output-188 rule).<br>Check `abs(variance_pct) > tolerance_pct (3.0%)`. | Variances Computed & Alerts Raised | Variance percentages stored on run; alerts raised for **Oil Consumption (`+5.0%`)** and **Packet Yield (`-6.0%`)** (and damaged packaging if output-scaled `+3.19%`), visible immediately on Supervisor & Owner dashboards. |
| **B6** | Production Supervisor / Admin (Desktop/Tablet) | Records **Overheads** for Run (or Month) & computes **Cost per Packet** | Enter direct labour (`₹1,200.00`) and gas/power (`₹600.00`) for the run (validation: `>= 0`). Sum:<br>`Material Cost + Packaging Cost (incl. damaged) + Direct Overheads + Allocated Monthly Overheads`. Divide by `actual_good_packets (188)` using integer-paisa math. | Run Costed | Total Run Cost (`₹5,810.00` FIFO / `₹5,855.00` WAvg) & Cost per Packet (`₹30.90` FIFO / `₹31.14` WAvg) persisted; gross margin against selling price (`₹50.00`) computed (`₹19.10` / `38.20%` FIFO, or `₹18.86` / `37.72%` WAvg). |

> **Alternative Single-Step Floor Entry:** While the benchmark demonstrates starting a run (`B3`: issue RM) and then recording output (`B4`), small floor teams sometimes record an entire completed batch in one go. Our state machine cleanly supports **both**: `Start Run (IN_PROGRESS)` -> `Complete Run (COMPLETED)` as the two-step default, plus an explicit *"Create & Complete Run"* convenience flow that executes `B3 + B4` atomically!

## 3. Workflow C: Month-End Audit & Reporting Loop

| Step | Actor | Action | System Behaviour & Data Sources | Final Output |
| --- | --- | --- | --- | --- |
| **C1** | Accountant / Auditor (Read-Only Desktop) | Selects date range (e.g. `01-Nov-2026` to `30-Nov-2026`) | Queries immutable posted invoices, credit notes, purchase receipts, production runs, stock ledger movements, and payment allocations within date bounds. | Deterministic read-only report datasets (no ability to alter underlying ledger). |
| **C2** | Accountant / Auditor | Reviews & exports **Sales & GST Reports** | Aggregates `TaxInvoice` (`POSTED`) and `CreditNote` (`POSTED`) into: Sales Register, Customer-wise Sales, Product-wise Sales, and GSTR-1/3B-shaped Outward Supply Summary (B2B vs B2C, HSN summary, Taxable, CGST, SGST, IGST). | Downloadable CSV/Excel & PDF reports matching invoice totals to the paisa. |
| **C3** | Accountant / Auditor | Reviews & exports **Purchase, Stock & Production Reports** | Reconciles Stock Summary (`Opening + Receipts - Issues/Sales ± Adjustments = Closing`) directly from `StockLedger`; pulls Production Variance & Costing report (planned vs actual material, yield, wastage, overhead, cost/packet). | Auditor-ready CSV/Excel & PDF trails where every closing balance clicks through to its exact source documents. |
| **C4** | Accountant / Auditor | Reviews **Collections & Receivables Ageing** | Computes Customer AR (`Invoices - Credit Notes - Payments`) and buckets open invoices into ageing slabs (`Current / 0–30 / 31–60 / 61–90 / 90+ days`). | Exportable AR Ageing and Collections register matching Retailer A `₹3,875.00`. |
